# 草记（Android）

对标 OPPO AI 心力球的手机端实现：**持续记录日常沟通 → 自动转写 → 拆分事件、生成摘要与待办 → 跨场景项目归集 → 行为觉察**。

与心力球的差异（按你的需求）：
- **触发机制**：**手机连上蓝牙耳机后**才开始记录（不用手动开关，也避免 24 小时乱录）
- **通话覆盖**：通过读取手机自带「通话录音」文件，把**来电/去电通话内容**纳入记录（微信语音见下方说明）

## 一、先看能力边界（很重要）

| 需求 | 是否可行 | 说明 |
|------|---------|------|
| 蓝牙耳机连接触发录音 | ✅ 可以实现 | 监听 HFP/A2DP 连接广播 |
| 现场对话记录 | ✅ 可以实现 | 麦克风录音（耳机麦克风或手机麦克风） |
| **来电/去电通话内容** | ⚠️ **间接实现** | Android 10 起第三方 App **无法**录制通话音频（`VOICE_CALL` 源已移除）。本 App 通过**读取系统自带「通话自动录音」生成的文件**实现——需手机系统支持通话录音（ColorOS 支持） |
| **微信语音通话内容** | ❌ **无法实现** | 微信语音不经系统通话通道，且微信会主动静音内录通道；屏幕录制同样录不到。这是全行业限制（录音笔、Plaud 等也同样做不到） |
| 转写 + 摘要 + 待办提取 | ✅ 可以实现 | 接云端 ASR + 大模型 |
| 项目归集 / 行为洞察 | ✅ 可以实现 | 大模型分类 + 本地统计 |

> 如果系统通话录音文件拿不到（例如 ColorOS 未开启通话自动录音），App 依然可用：现场对话正常记录，通话部分只能靠录音笔/另一台设备补录。

**合规提醒**：录音涉及他人声音，请遵守《个人信息保护法》《民法典》相关规定——建议开启系统通话录音的提示音、明确告知对方、仅作个人工作记录，不得用于非法目的或公开传播。

## 二·五、针对用户反馈的四项改进（v1.1）

心力球用户反馈的四个问题，本版本逐条处理：

### ① 界面不够精细 → 统一设计规范
- 新增 `res/values/dimens.xml`：间距（4/8/12/16/20 八倍体系）、圆角（10/18/25）、字号（21/16/13/11/10）全部收口
- 卡片改用 `bg_card_ripple`：**按压有青绿涟漪反馈**，不再"点下去没反应"
- 卡片间距、内边距、行距、标签高度全部统一；页标题层级固定（21sp 粗 / 12sp 副语）
- 场景与质量信息合并进卡片副行，不做额外堆叠

### ② 声纹分辨力不够、说话对象搞不清 → 机器分人 + 人工订正 + 记忆
- 现实：手机端跑声纹嵌入模型（ECAPA/CAM++）包体大、准确率受录音质量限制
- 本方案：**转写端做 diarization 分人 → 用户在详情页点一下改名 → 系统记住**
  - `data/SpeakerMap.kt`：全局「说话人标签 → 真实姓名」映射（持久化）
  - 详情页「说话人」区：列出本次出现的所有说话人，点击可改成「我 / 张总 / 王工」
  - 改名后：**本条记录内全部替换**，且**之后所有新记录自动沿用**
  - 配合设置页「我是说话人几」，新记录直接标出「我」
- 效果：即使分不准，两次操作后把说话人稳定下来，且不串号

### ③ 不区分环境、不够智能 → 录音后离线音频分析
- `audio/AudioProbe.kt`：录音结束后解码 PCM（MediaExtractor + MediaCodec），逐 20ms 算能量
- 产出：**底噪 dBFS / 有效人声占比 / 峰值 / 动态范围** → 判定四类场景
  | 场景 | 判定依据 | 处理 |
  |------|---------|------|
  | 安静独处 | 底噪 ≤ -48dB 且说话占比 < 45% | 按灵感处理 |
  | 会议交谈 | 底噪低、说话密集 | 按会议处理，跨场景归集 |
  | 嘈杂环境 | 底噪 ≥ -32dB 且动态 < 14dB | 提示"环境较吵，建议靠近说话人" |
  | 无有效人声 | 说话占比 < 5% 或峰值 < -42dB | **不出记录、不留音频**（直接跳过） |
- 场景写进记录并在卡片显示（如「2分30秒 · 会议」），也作为上下文传给大模型（会议就找结论待办，独处就提炼想法）
- **最大价值：「只有噪音的录音直接丢弃」，从源头切断"AI 拿垃圾内容乱写摘要"**

### ④ AI 总结跑题乱写 → 三层治理
| 环节 | 措施 | 实现 |
|------|------|------|
| 进口 | 转写清洗：去重复行、去纯语气词、折叠高度相似句；有效字数 < 6 直接跳过不调模型 | `ai/TranscriptCleaner.kt` |
| 中段 | 长文本 **map-reduce**：>1800 字先分块抽要点（只抄事实、最多 8 条），再写摘要；prompt 强约束"只依据原文、不推测、拿不准留空"，温度降到 0.2 | `ai/LlmClient.kt` |
| 出口 | **`ai/SummaryGuard.kt` 规则校验**：摘要里的数字/金额/百分比必须能在原文找到；关键短语回扣率 < 35% 判为可疑；**待办找不到原文依据直接丢弃**；重合度过低自动降温度重试 1 次 | `ai/SummaryGuard.kt` + 重试逻辑 |
| 兜底 | 校验不过 → 记录标 `需确认`（列表橙字 + 详情页橙色提示条）；摘要支持**直接编辑**，改完清除标记 | `SessionDetailActivity` |

> 设计原则：**宁可少写，不可乱写**。待办宁可丢 1 条，也不给用户一条编造的待办。

## 三·八、本人声纹（v1.5 新增）

目标：录一次自己的声音，之后每次录音**自动认出哪几段是「我」说的**，不再需要手动指定「我是说话人几」。

### 用法（3 步）

1. 设置 → **本人声纹** → 「录入声纹」
2. 朗读页面上的提示句约 15 秒（安静环境、手机离嘴 20~30cm、正常语速）
3. 之后录音：转写完成时自动判定，详情页显示「**声纹：已自动识别 · 我 = 说话人1（匹配度 98%）**」

设置页可随时**重新录入 / 清除**，并可单独关闭「用声纹自动识别」。

### 实现（全部在手机本地，不联网、不上传声音）

| 步骤 | 做法 | 代码 |
|---|---|---|
| 特征提取 | 流式解码音频（逐块处理，30 分钟通话也不占内存）→ 25ms/10ms 分帧 → 预加重 + 汉明窗 → 512 点 FFT → 26 通道梅尔滤波 → DCT 得 13 维 MFCC；丢弃 c0（抗音量差异） | `audio/MfccScanner.kt` |
| 特征向量 | 有声帧上取 **12 维 MFCC 均值 + 12 维一阶差分均值 + 1 维基频（对数）** = 25 维，加权（MFCC 1.0 / 差分 0.7 / 基频 1.6）后 L2 归一化 | 同上 |
| 有声帧判定 | 用能量 15 分位作底噪、95 分位作峰值，阈值 = 底噪 + max(6dB, 0.30×动态范围) | 同上 |
| 分段归属 | 用转写返回的「说话人 + 起止毫秒」把每一帧归到对应说话人，**按人分别累积**（内存只与人数有关，与录音时长无关） | 同上 |
| 判定 | **中心化余弦**：先减去「模板 + 本次所有候选」的共同分量再算夹角；第一名与第二名的差距经 logistic 换算成 0~1 匹配度，≥80% 才自动采用 | `audio/Voiceprint.kt` |
| 存储 | 25 维向量 + 样本时长 + 录入时间，JSON 存在本机 SQLite 的 settings 表 | 同上 |

### 为什么用「中心化余弦 + 相对匹配度」而不是直接算相似度

直接算余弦时，同一人约 0.99、不同人也有 0.95~0.98 —— 数值都很高，无法设阈值。
减掉所有候选与模板的共同分量后，差异被放大到可判别区间：**明显不同的人差距约 0.09，音色接近的人差距约 0.004**（相差 20 倍以上）。
由于绝对值本身不好解读，界面统一显示换算后的「匹配度 %」。

### 阈值标定（离线实测，可复跑）

`docs/voiceprint-validation.py` 把同一套算法在 Python 里逐行复刻，用合成嗓音跑判定（无 numpy，纯标准库）：

```bash
python docs/voiceprint-validation.py
```

标定结果（T = 0.008，门槛 80%）：

| 场景 | 第一名与第二名差距 | 匹配度 | 决策 |
|---|---|---|---|
| 男声录入 vs 男+女对话 | 0.092 | 100% | 自动采用 ✅ |
| 女声录入 vs 同一对话（反向） | 0.092 | 100% | 自动采用 ✅ |
| 三人会议，其中一人音色接近 | 0.013 | 84% | 自动采用 ✅ |
| 同性别且音色接近（113Hz vs 150Hz） | 0.004 | 63% | **不采用**，保留人工设置 ✅ |
| 单人会话（只有自己） | — | — | 跳过判定（无比较对象）✅ |

> 阈值集中在 `Voiceprint.kt` 的两个常量：`T_MARGIN = 0.008`、`MIN_CONFIDENCE = 0.80`。
> 真机上如果发现「该认出的没认出来」，把 `T_MARGIN` 调大（如 0.012）会更容易自动采用；
> 如果发现「认错人」，把它调小并提高 `MIN_CONFIDENCE`。

### 能力边界（务必知晓）

- 用的是 **MFCC + 音高的轻量统计模型**，不是深度学习声纹库（ECAPA-TDNN / CAM++ 这类模型要几十 MB 且在手机上推理耗电）。
  因此：**男女声、音色差异明显的人区分度很好；同性别且音色接近的两人可能分不准**。
- 判定不足时的行为是「**不猜**」：保留你手动指定的「我是说话人几」，并在详情页标注「把握不足（匹配度 xx%）」。
  这时点一下详情页「说话人」里的标签改成「我」，App 会**记住**（`SpeakerMap`），之后同一个人都会沿用。
- 声纹判定依赖转写服务返回**带时间戳的说话人分段**（`segments[].speaker/start/end`）。
  服务只返回纯文本时自动跳过，不影响其它功能。
- 声纹数据只在本机数据库；换手机 / 卸载重装需要重新录入。

## 三·九、蓝牙耳机连接稳定性（v1.6 重点修复）

现象：耳机明明连着，App 里会突然变成「未连接」，正在进行的记录被中断；或者连上耳机时重复提示、重复开始。

### 根因（旧代码逐条对照）

| # | 根因 | 旧代码 | 后果 |
|---|---|---|---|
| ① | **把中间态当成断开**（主因） | `state != STATE_CONNECTED` 即视为断开，`STATE_CONNECTING` / `STATE_DISCONNECTING` 也被算进去 | 开始录音时系统要切音频通路（A2DP ↔ HFP），两个 profile 先后上报中间态，出现「两侧都不是 CONNECTED」的空窗 → **误判断开 → 录音被自己停掉**，随后又连上 → 再开一段新录音 |
| ② | 只靠广播，会漏 | 注册时只挂广播，无主动查询 | App 在后台/被省电策略限制时收不到广播；耳机在打开 App 前就连好 → 界面长期显示「未连接」 |
| ③ | 单设备布尔值 | `hfpConnected` / `a2dpConnected` 两个 Boolean | 连第二副耳机、或同一副耳机同时挂 A2DP+HFP 时状态互相覆盖 |
| ④ | 不用耳机麦时也没释放 SCO | 录音只设 `AudioSource.MIC`，从不管理 SCO | 上次异常退出若残留 SCO，耳机会被卡在通话通路：听歌变闷、声音断续，严重时系统判定异常而断连 |
| ⑤ | 前台服务 START_STICKY | 进程被杀后系统反复拉起空服务 | 留一个空跑的前台通知，看起来像「一直在录音其实没录」 |

### 修复

| 修复 | 做法 |
|---|---|
| **只认终态** | 仅处理 `STATE_CONNECTED` / `STATE_DISCONNECTED`，`CONNECTING` / `DISCONNECTING` 直接忽略 |
| **断开宽限期 3 秒** | 检测到「两路都断开」后不立即停止，等 3 秒；期间任一路恢复就**撤销**（切通路、短暂丢包都不再误停） |
| **连接去抖 0.5 秒** | 等 A2DP/HFP 都上报完再触发一次，避免重复开始录音 + 重复 Toast |
| **按设备地址集合记录** | `LinkedHashMap<address, name>`，两路取并集，多设备/双 profile 都不会错判 |
| **主动校正** | 注册时 + 每次回到前台，用 `getProfileProxy` 读一次真实连接设备列表，覆盖本地状态（补齐漏收的广播） |
| **蓝牙关闭立即断开** | 监听 `BluetoothAdapter.ACTION_STATE_CHANGED`，关蓝牙不等宽限期 |
| **SCO 生命周期** | 新增 `audio/BluetoothSco.kt`：用耳机麦前才起 SCO，停止录音 / 服务销毁 / 切回手机麦时**一定释放** |
| **音源默认不变** | 默认仍是手机麦克风（44.1kHz），完全不改动蓝牙音频通路 —— 这是最稳的路径 |
| **前台服务改 NOT_STICKY** | 进程被杀后不反复拉起空服务；空 intent 启动时若无录音任务直接退出 |

### 新增开关：「用蓝牙耳机麦克风录音」（默认关闭）

| | 手机麦克风（默认） | 蓝牙耳机麦克风 |
|---|---|---|
| 音质 | 44.1kHz | 蓝牙通话通路 8~16kHz，**明显较低** |
| 距离 | 手机放桌上也能录 | 离嘴近，远处说话更清楚 |
| 对蓝牙连接的影响 | 不动音频通路，最稳 | 会切 SCO，期间耳机音乐被打断 |
| 适合场景 | 会议、桌面、日常 | 走动、耳机一直戴着 |

> 若你遇到耳机连接不稳，**保持关闭**。开关位置：设置 → 记录行为下方。

### 状态机验证（可复跑）

`docs/bluetooth-state-machine.py` 用虚拟时钟把去抖状态机逐条推演（7 个场景）：

```bash
python docs/bluetooth-state-machine.py
```

| 场景 | 期望 | 结果 |
|---|---|---|
| 录音中系统把 A2DP 切到 HFP（中间 1.5s 两侧都不是 CONNECTED） | 不中断 | ✅ |
| 耳机真的拔掉（两路都断开） | 3 秒后停止 | ✅ |
| 短暂断连 2 秒内自动恢复 | 不中断 | ✅ |
| 只断 A2DP、HFP 仍连接 | 不中断 | ✅ |
| 连接时两路相继上报 | 只触发一次 | ✅ |
| 关掉蓝牙 | 立即断开 | ✅ |

### 二、耗电优化（依据实测的耗电点逐条处理）

| # | 原来的耗电点 | 问题量级 | 现在 |
|---|---|---|---|
| ① | **通知栏每秒刷新**：`nm.notify()` 每秒一次更新「已记录 mm:ss」 | 录 1 小时 = **3600 次**跨进程通知更新，每次都会唤起系统 UI 重绘 | 改用 `setUsesChronometer(true)` + `setWhen(startAt)`，时长由**系统自己渲染**，App 一次都不发（只在「标记重点」时更新 1 次） |
| ② | **主界面每秒重建今日列表**：`todayFragment.refresh()` 每秒查库 + RecyclerView 全量重绘 | 打开 App 挂着 = **每分钟 60 次**数据库查询与列表重绘 | 只在**录音开始/结束状态变化**时刷新（一次录音 2 次）；空闲时计时器从 1s 降到 **5s** 只做状态检查 |
| ③ | **环境分析整段解码**：录音结束后把整段音频解码一遍算能量 | 30 分钟录音要解码 30 分钟音频 | 只取**前 3 分钟**样本（判断安静/会议/嘈杂足够），解码量降约 **90%** |
| ④ | **声纹分析整段跑 FFT**：每个 10ms 帧都做 512 点 FFT + 26 通道梅尔 + DCT + 自相关基频 | 30 分钟会议 = 18 万个 FFT | 只对**目标说话人片段**做特征，且每人**最多 90 秒**（9000 帧）；其余帧只留能量（几乎零成本）。计算量从「整段时长」降到「说话人数 × 90 秒」 |
| ⑤ | **录音码率 128kbps** | 1 小时约 56MB，编码与写入更费 | 降到 **64kbps**（语音转写完全够用），文件体积与编码开销约减半 |

> 关于「为什么不加 WakeLock」：录音期间音频硬件本身会让系统保持唤醒，额外加 WakeLock 只会更费电，所以没加。
> 也不做任何定时轮询/定位等高耗电行为——App 在没有录音时基本处于静默状态。

### 三、锁死与自动退出：逐条修根因

| 现象 | 根因 | 修复 |
|---|---|---|
| **录完音界面卡死无响应（ANR）** | `stopRecordingAndSave()` 在**主线程**调 `AudioProbe.analyze()` 解码音频，几百毫秒到数秒 | 分析 + 入库移到后台线程；期间前台通知改为「正在整理录音…」保住优先级；收尾统一走 `finishService()` |
| **用着用着自动退出（Android 12+）** | App 在**后台**时 `startForegroundService` 抛 `ForegroundServiceStartNotAllowedException` ——「耳机连上时 App 恰好在后台」必踩 | MainActivity / TodayFragment 全部 `runCatching`，失败降级为「点击开始记录」通知 |
| 点开始后直接闪退（权限被收回等） | `startForeground` 抛异常把服务连同进程带走 | `startForeground` 包 `runCatching`，失败则安静结束本次录音 |
| 服务内异常导致整个 App 退出 | `onStartCommand` 无兜底 | 拆出 `handleCommand()`，外层统一捕获 |
| 切「项目」「觉察」页卡顿 | 觉察页主线程读 **1000 条**含全文摘要；项目页读 **500 条**再分组 | 觉察页改后台取数 + 主线程刷 UI；项目页改 `GROUP BY` 聚合查询（`Repo.projectSummaries`，只回名称/条数/最近时间） |
| Android 8/9 上时长识别失败 | `MediaMetadataRetriever` 到 API 29 才实现 `AutoCloseable`，`.use {}` 在旧系统抛 `NoSuchMethodError` | 改 `try/finally + release()` |
| 崩溃后无法排查 | 没有任何日志 | `App` 装全局未捕获异常处理器，写 `filesDir/crash_last.txt`（**不吞异常**，仍交系统处理） |

另外移除了声明但未使用的 `WAKE_LOCK` 权限（录音期间音频硬件本身保持唤醒，不需要额外的唤醒锁）。

## 六、说话人区分（我 / 对方）怎么用

1. 「设置」→ 打开 **转写时启用说话人分离**（默认开）

```
[我] 可以，我这周跟进。
```

4. 大模型拿到带角色的文本后，摘要会明确区分「我承诺了什么 / 对方提出了什么」，洞察也按「我」的视角写。

> 说明：说话人分离能力取决于转写服务是否支持 diarization。
> - 支持（返回 segments/utterances 带 speaker）→ 自动标注说话人
> - 不支持（只返回纯文本）→ 自动降级为无角色文本，不影响其它功能
> 你只需要在设置里选一次「我是说话人几」，App 负责把标签换成「我 / 对方」。

## 七、待办到期提醒怎么用

1. 记录分析后，待办会自动带到期日（模型把「下周五」「月底前」这类相对时间换算成具体日期）
2. 「记录详情」里点某条待办下方的日期 → 可手动改到期日
3. 「觉察」页顶部会显示：今天到期 X 项 / 已逾期 Y 项
4. 「设置」→ **待办提醒**：可开关、可设每日提醒时间（默认 09:00）

提醒触发时机：
- 每日设定时间（AlarmManager，非精确闹钟，误差几分钟，无需特殊权限）
- App 每次启动时检查一次
- 新待办生成后立即检查一次

通知内容形如：**待办提醒 · 已逾期 2 项 · 今天到期 1 项**，正文列出前 3 条。

## 三·十二、说话人能力的「真话化」（v1.9）

起因：核对硅基流动官方文档时发现，`/v1/audio/transcriptions` 的响应体**只有** `{"text": "..."}`，
不返回 `segments` / `speaker`。而 v1.5 的声纹识别要靠「带时间戳的说话人分段」去录音里切样本，
也就是**默认配置下声纹永远不会触发**，设置页却写着「支持说话人」——又一个会被用户打成「名不副实」的点。

### 改了什么

| 位置 | 原来 | 现在 |
|---|---|---|
| `ai/Providers.kt` | 硅基流动 `supportsDiarize = true`，名字写「支持说话人」 | `false` + 名字改「仅纯文本」，并给该字段补上判定标准（要能返回 `segments[].speaker` 才算支持） |
| `ai/AsrClient.kt` | 只要开关打开就发 `verbose_json` / `diarize` / `speaker_labels` / `timestamp_granularities[]` | 新增 `diarizePossible()`：预设明确纯文本的服务**根本不发**这些扩展参数（发了也拿不到，个别服务还会因未知参数 400）；自定义服务仍尊重用户开关 |
| `ai/AsrClient.kt` | 一次请求定生死 | 拆出 `execute()`，扩展参数被拒（400/422）时**自动降级纯文本重试一次**，让「不支持分段」表现为降级而不是「一条都转不出来」 |
| `ui/SettingsFragment.kt` | 开关只是摆着 | 新增 `applyAsrCapability()`：选到纯文本服务时**关闭并禁用**「说话人分离」与「我是说话人」下拉，提示文案按真实能力切换（`speaker_tip_plain` 会带上服务商名） |
| `ui/SettingsFragment.kt` | 声纹区只讲命中率 | 纯文本服务下补一句「当前服务不返回分段，声纹暂时无法自动识别『我』，换服务后即刻生效，不用重录」 |
| `ui/EnrollVoiceActivity.kt` | 存完就说「以后会自动判断」 | 按能力分支：不支持时如实说明，并强调**声纹本身不用重录** |

### 为什么没顺手做「本地说话人分离」

技术上可以：用已有的 `MfccScanner` 做帧级 MFCC + 聚类，切出说话人轮次，再按轮次**分段上传转写**。
但代价是 N 次请求（一段几分钟的对话可能几十个轮次），且文本与说话人的对齐完全依赖本地切分精度——
在没真机验证前硬上，很可能把「说话人搞不清」从「不区分」升级成「乱区分」，比现状更糟。
所以这一版先把**能力宣称与实际行为对齐**，本地分离作为下一步单独评估。

## 三·十三、内页 logo 玻璃托底 + 响应优化（v1.10）

### 一、内页 logo：圆形玻璃质感

**问题**：品牌标本身是**正红圆角方块**，内页顶栏也是**正红**——红压红，logo 的轮廓直接消失，
只剩一个悬空的白 C，看起来像「随便贴了个字母」，不像品牌标识。

**做法**：在 logo 下面垫一层**白色磨砂圆**，把它从红底上「托」出来。

> ⚠️ 这一版的做法在 **v1.22 已被替换**：白描边 + 内缩方块最终读成「一条白线 + 一个内框」，
> 标本身仍是平的。现行做法见「三·二十五」。此处保留，作为设计演进记录。

| 层 | 参数 | 作用 |
|---|---|---|
| 玻璃本体 | 白 25%（`#40FFFFFF`） | 透出底下的红，是玻璃不是白贴纸 |

| 高光描边 | 白 65%，1dp（`#A6FFFFFF`） | 勾出圆的边界——玻璃感最关键的细节 |

留白比例统一约 0.6，避免 logo 顶满显得挤。

覆盖位置：主页顶栏、记录详情、项目详情、语音速记、声纹录入——**全部内页顶栏都有**，品牌识别不再断层。

> 视觉验证：`docs/logo-glass.png`（由 `docs/logo-glass-mock.py` 用纯 PIL 按同一套参数生成，
> 左边还原 v1.9 的「红压红」、右边是改后效果，不装 APK 也能判断）。
> 全程不用 `blur` / `shadowLayer`：纯色层叠加，零额外合成开销——与 v1.7 的省电目标一致。

### 二、响应优化：把主线程上的活挪走

用户反馈「响应慢」，逐处查下来都不是「代码慢」，而是**该在后台做的活压在主线程上**：

| # | 问题（改前） | 改后 |
|---|---|---|
| 1 | **列表绑定逐条查库（典型 N+1）**：`SessionAdapter` 在 `onBindViewHolder` 里调 `Repo.todosOf()`，一屏 8 条就 8 次查询，每次滑动重跑 | 新增 `Repo.todoCounts(ids)`，一次 `GROUP BY` 查全，绑定阶段只剩 `Map` 查找 |
| 2 | **今日页查库在 UI 线程**：一次读最多 50 条**带完整转写/摘要**的记录 | `refresh()` 全部搬到后台线程，主线程只做 `submit` + 文案；新增 `@Volatile loading` 防重入 |
| 3 | **切底部导航就重建页面**：每次 `new Fragment + replace`，等于重新 inflate 视图、重新查库 | 改 **add/hide/show 复用** + `setReorderingAllowed` + `commitNow`（保证连点两个 Tab 时状态不错乱），各页补 `onHiddenChanged()` 触发刷新，`onResume` 里 `if (!isHidden)` 少做一次无用查询 |
| 4 | RecyclerView 未声明固定高度 | 三个列表加 `setHasFixedSize(true)` + `setItemViewCacheSize(8)` |
| 5 | **项目详情页打开先卡一下**：主线程查该项目全部记录，再一次性 `addView` 几百个卡片 | 查库移 IO；卡片**每 12 条一批** `addView`，批间 `post` 让出主线程——首屏立刻出现，其余补齐；「生成洞见」的读库也移 IO |
| 6 | 启动时在主线程「查库 + 建通知」（`TodoReminder.checkAndNotify`） | 只把闹钟设置留在主线程（跨进程调用很快），查库建通知放后台线程 |

**没做的事（有意）**：没有引入 Room / 协程 Flow 重构数据层。当前数据量级（本地千条内）下，
把查询挪出主线程 + 消掉 N+1 已经能解决观感问题；大改数据层会引入迁移风险，收益不成比例。

## 三·十四、整理导出 + 微信/笔记/日历打通（v1.11）

### 一、能力一览

| 能力 | 入口 | 走什么协议 |
|---|---|---|
| 复制全文 | 记录详情 → 整理与分发 → 复制全文 | 剪贴板 |
| 导出文稿（.md） | 记录详情 → 导出文稿 | SAF（`ACTION_CREATE_DOCUMENT`），自己选存哪 |
| 转发微信 | 记录详情 → 转发微信 | `ACTION_SEND` + `setPackage("com.tencent.mm")` 直达 |
| 存到便签 | 记录详情 → 存到便签 | 自己列一份「能收文字的应用」清单，点一下直达 |
| 单条待办进日历 | 记录详情 → 把待办加入系统日历 | `ACTION_INSERT`（**不需要权限**） |
| 导出今日 / 全部记录、待办清单 | 设置 → 整理导出与系统打通 | SAF |
| 批量待办同步到日历 | 设置 → 把未完成待办同步到系统日历 | `CalendarContract`（需读写日历权限） |
| **反向接收**：别的应用分享文字给草记 | 任意应用 → 分享 → 草记 | `ACTION_SEND` intent-filter |

### 二、几个关键决定

**1. 一份文稿，四处复用**
导出、复制、微信、便签用的都是 `Exporter.sessionMarkdown()` 生成的同一段 Markdown——
不会出现「发微信的文字和导出的文件内容不一样」。

**2. 微信只能到「选择聊天」这一步**
微信没有开放「直接发到指定好友」的接口，任何 App 都做不到。
`ACTION_SEND` + `setPackage` 会直接拉起微信的「选择聊天」界面，用户点一下联系人才发出。
这是平台限制，不是实现取舍；点「转发微信」后如果微信未安装，会自动回退系统分享面板。

**3. 便签列表为什么要自己筛**
系统分享面板里混着蓝牙、打印、各种 SDK，用户得在一屏图标里找「便签」。
`ShareTargets` 先按已知包名（`com.coloros.notepad` / `com.oplus.notepad` / Keep / 印象 / 有道 / Obsidian…）
再按名称关键词（便签、记事、笔记、备忘录、note…）筛一份短列表，点一下直达；
一个都没匹配到才回退系统面板——不会出现「点了没反应」。

**4. Android 11+ 的包可见性（必须声明，否则列表是空的）**

```xml
<queries>
    <intent>
        <action android:name="android.intent.action.SEND" />
        <data android:mimeType="text/plain" />
    </intent>
</queries>
```

没有这段，`queryIntentActivities` 在 Android 11+ 会返回空列表，
表现为「存到便签」点开一个空对话框——这是接入分享最容易漏的一步。

**5. 日历的两种写法**
- 单条：`ACTION_INSERT` 打开系统日历的「新建日程」界面，用户确认后保存，**完全不需要权限**，最稳。
- 批量：直接 `ContentResolver.insert(Events)`，需要 `READ/WRITE_CALENDAR`。

全天事件的坑：`ALL_DAY=1` 时 `DTSTART` / `DTEND` 必须是 **UTC 午夜**，且 `EVENT_TIMEZONE` 必须是 `"UTC"`。
按本地时区写会让事件整体偏一天——这是接日历最典型的错误（见 `CalendarBridge.utcMidnight`）。
批量写入前还会按「标题 + 日期」查一遍已存在的事件，重复点不会造出一堆重复日程。

**6. 反向接收，才算真打通**
只把记录送出去是单向的。MainActivity 注册了 `ACTION_SEND text/plain`，
在微信/浏览器/任意笔记里选中一段文字 → 分享 → 草记，就会立刻落成一条记录
（来源标记「外部导入」）并走同一条分析流水线，自动生成摘要与待办。

### 三、没做 / 做不到

| 想法 | 结论 |
|---|---|
| 直接把记录发到某个微信群 / 好友 | 微信未开放接口，只能到「选择聊天」 |
| 写入微信「收藏」 | 无公开接口 |
| 读取 OPPO 便签已有内容 | 便签没有公开 ContentProvider，只能「送进去」，不能「读出来」 |
| 双向同步日历（改动回写草记） | 需要长期监听 `CalendarContract` 变更，本版只做单向写入 |

## 三·十五、代码审计与优化（v1.12）

全量过了一遍约 3500 行 Kotlin，按「真 bug / 性能 / 规范」三类处理。
没有为了「看起来优化了」去改结构，下面每一条都写清改前的问题在哪。

### 一、真 bug（4 项）

| # | 问题 | 为什么是 bug | 改法 |
|---|---|---|---|
| 1 | **`TimeUtil` 用单例 `SimpleDateFormat`** | `object` 里的三个 formatter 被多处**并发**使用（今日页后台线程、Pipeline 的 IO 线程、导出线程都调 `dateFull`）。`SimpleDateFormat` 内部持有可变 `Calendar`，并发会输出**错误日期**，极端情况抛 `ArrayIndexOutOfBoundsException` —— 典型「偶发、难复现、被 runCatching 吞掉」的脏 bug | 换 `java.time.DateTimeFormatter`（不可变、线程安全；minSdk 26 原生可用） |
| 2 | **`AnalysisPipeline` 注释写「串行队列」，代码其实是并发** | 只做 `running` 去重，然后各自 `scope.launch`。导入十段录音会同时打十几个转写/摘要请求，这正是 429（限流）的主因 | 加 `Mutex`，`serial.withLock { process(...) }` 真正串行 |
| 3 | **觉察页每次刷新都 `new Thread`** | 快速切页会叠起多个「读 1000 条」的线程，白烧 CPU 和电池 | 加 `@Volatile loading` 防抖 |
| 4 | **勾一下待办就整页重建** | `render()` 会重查会话 + 重查全部待办 + 重建所有说话人 chip，视觉上整页闪一下 | 改成只更新这一行（删除线 + 到期日变灰） |

## 三·十六、安全与隐私加固（v1.13）

这个 App 的性质决定了它天然装着一堆敏感东西：**通话录音、会议原文、待办里的人和钱、API Key**。
所以先明确「防谁」，再逐条落措施——不做没有威胁模型对应的「安全表演」。

### 一、威胁模型

| 场景 | 具体后果 |
|---|---|
| 手机丢失 / 借给别人 | 打开就能看到全部对话摘要 |
| 截屏、投屏、录屏演示 | 会议内容被顺手截走 |
| 最近任务（多任务）界面 | 缩略图里就是完整摘要，放在桌上就被人看到 |
| 云备份 / 换机克隆 | 私人录音被系统复制到云端或另一台设备 |
| 数据库文件被 adb / root / 备份取走 | API Key 明文躺在 `settings` 表里，可直接盗用 |
| 接口地址填了 http:// | 整段录音 + 对话 + Key 在同一 Wi-Fi 下明文裸奔 |
| 锁屏通知 | 待办原文（催款、人名、金额）显示在锁屏上 |
| 复制到剪贴板 | Android 13+ 剪贴板预览与剪贴板历史里留下完整内容 |

### 二、具体措施

| # | 措施 | 实现 |
|---|---|---|
| 1 | **API Key / 声纹模板加密落库** | `util/SecureStore.kt`：Android Keystore 内生成 AES-256 密钥（不可导出），AES/GCM/NoPadding 加密，格式 `enc:v1:<base64(iv|cipher)>`。密钥在 TEE，**不随备份导出**；旧版本存的明文在第一次读到时就地加密（惰性迁移） |
| 2 | **关闭云备份与换机克隆** | `allowBackup=false` + `fullBackupContent=false` + `res/xml/data_extraction_rules.xml`（cloud-backup 与 device-transfer 全排除）。换机改用应用内「导出全部记录」，去向由用户自己控制 |
| 3 | **截屏 / 录制 / 最近任务保护** | `FLAG_SECURE`，作用于全部 5 个页面；默认开启，可在设置里关（有人需要截图分享给同事） |
| 4 | **强制 HTTPS** | 双保险：`res/xml/network_security_config.xml` 在系统层禁明文；`util/EndpointGuard.kt` 在发请求前拦一道并给中文提示。例外只有 `127.0.0.1 / localhost`（自建服务本机调试，流量不出设备） |
| 5 | **锁屏通知脱敏** | 待办提醒改 `VISIBILITY_PRIVATE` + `setPublicVersion()`：锁屏只显示「草记 · 有待办需要处理」，解锁后才展开真实内容 |
| 6 | **剪贴板敏感标记** | Android 13+ 给 `ClipData` 打 `EXTRA_IS_SENSITIVE`，系统不再显示内容预览、也不入剪贴板历史 |
| 7 | **一键清除本机全部数据** | `Repo.wipeAll()`：记录、待办、洞见、配置（含加密的 Key 与声纹）、录音文件；二次确认并提示先导出 |
| 8 | **首启数据说明 + 设置页隐私区块** | 第一次打开时说明「数据在哪 / 是否上传 / 加密状态 / 备份已关」；设置页展示实际加密状态（`SecureStore.isAvailable()` 自检，不是写死一句「已加密」） |
| 9 | **日志脱敏** | 错误日志只保留前 60 字，避免接口响应片段（可能含文本）留在 logcat |

### 三、边界：这些没做，以及为什么

| 项 | 说明 |
|---|---|
| 整库加密（SQLCipher） | 要换掉 `SQLiteOpenHelper` 并处理密钥与迁移，风险大于收益。当前依靠**应用私有目录 + 系统沙箱**（其他应用无 root 读不到），敏感字段已单独加密 |
| App 启动生物识别锁 | 值得做，但需要处理「锁屏状态下耳机自动开始录音」的后台流程，本版先不动，列为后续可做 |
| 防 root / 防调试检测 | 可被绕过，且会误伤正常用户，属于「安全表演」，不做 |
| 导出文件 | 一旦写到你选的目录（或发到微信），就脱离应用保护范围，由你自己管理 |
| 上传内容 | 录音/文本发给你配置的服务商后，按其隐私政策处理——这是选择第三方接口的固有代价，App 能做的是**强制 https + 不主动上传** |

## 三·十八、长时间录音「什么都没录进去」的根因与修复（v1.15）

用户反馈：戴着耳机开了很久的持续记录，事后既没有对话也没有声音。排查出**四条各自都能独立造成这个结果**的原因，逐条修掉。用户猜的方向（被电话和微信语音打断）是其中最主要的一条。

### 一、四条根因

| # | 根因 | 后果 |
|---|---|---|
| 1 | **通话夺走麦克风，应用毫无察觉** | 来电 / 微信语音建立后，系统把麦克风交给通话，第三方录音流被**静默**（流还在，写进去全是静音）。代码既没监听通话状态、也没检查是否还有信号，`isRecording` 一直 true，通知栏计时器照走，用户以为在录 |
| 2 | **打断即整段报废** | 全程只有一个录音文件。被打断后这个文件后半段是静音、又没有正常收尾（MP4 缺 moov），等于整段作废 |
| 3 | **解码失败被当成「没人说话」→ 删文件** | `AudioProbe` 返回 `unknown`，其 `hasSpeech=false`，上层据此删除文件并提示「未检测到有效人声」。这是**数据丢失级**缺陷 |
| 4 | **长录音只看开头 3 分钟就判死** | 无论录多久都只解码开头 180 秒。若开头正好是静场、等待或被切断的空段，后面再多对话也会被判无人声而删掉 |

### 二、修复

| 措施 | 做法 |
|---|---|
| **通话检测** | 每 2 秒巡检 `AudioManager.mode`：进入 `MODE_IN_CALL` / `MODE_IN_COMMUNICATION` 即判定被打断。**不需要 READ_PHONE_STATE 权限**，也无需区分系统电话与微信 |
| **静默检测** | 同时看 `getMaxAmplitude()`：连续 10 秒严格为 0 即判定被静音（真实环境的本底噪声不会是 0） |
| **打断即分段保存** | 立刻收尾当前段 → 落库 → 保存已录部分，不删。等麦克风恢复后**自动接着录**新的一段，标题标「接上段」 |
| **定时切段** | 每 30 分钟自动切段，单段损坏最多丢 30 分钟；也避开转写接口的单文件时长/体积上限 |
| **区分「分析失败」与「没人声」** | `Profile` 新增 `analyzed`。只有**分析成功且确实无人声**才丢弃；分析失败一律保留并入库 |
| **多点采样** | 长录音取头 / 中 / 尾三个窗口判定，不再只看开头 |
| **OnErrorListener** | 录音器报错（麦克风被抢、编码器异常）立刻分段保存，原来完全静默 |
| **断连不停录音** | 通话建立时耳机音频通路切换会导致「假断连」。`onDisconnected` 里若处于通话中则只提示、不停记录 |
| **残留录音恢复** | 启动时扫描 `recordings/` 目录，把「不在记录表里、且 90 秒没被写过」的 `REC_*.m4a` 重新入库并转写。**已被旧版本误删的救不回来，但从未入库的能捞回** |
| **界面如实反映** | 等待续录时今日页显示「通话占用了麦克风，已暂停；通话结束后会自动接着录」，而不是显示「待命」诱导用户重开 |

### 三、做不到的事（必须说清）

1. **通话期间的对话录不到。** Android 从 10 起禁止第三方应用录制通话对端音频，这不是草记的实现问题。能做的只有：通话前的内容保住、通话后立刻接上。
2. **微信语音同理**，且在部分 ROM 上还会把整条音频通路锁死几十秒。
3. 需要通话本身的内容，只能开手机自带通话录音，事后再用设置页的「扫描系统通话录音并导入」。

- `versionCode='15' versionName='1.15'`，签名未变（可覆盖升级）

## 三·十九、手动手机麦克风（v1.16）

**需求**：除了「连上蓝牙耳机自动触发」，还要能手动指定用手机麦克风录。

**改动**：音源从「设置里一个藏起来的开关」变成「今日页底部可直接点的选项」。

| 位置 | 行为 |

| 未录音时点选 | 只改默认音源，下次开始生效（不打扰任何正在跑的东西） |
| **录音中点选** | 立即生效：当前这段先收尾保存（标题标「接上段」），紧接着用新音源开新段，**一句都不丢** |
| 「开始记录」按钮 | 把当前选中音源随 `EXTRA_SOURCE` 一起传给服务，避免刚选完又被设置页改回去 |
| 设置页开关 | 与今日页共用同一个偏好（`K_BT_MIC`），来回切换两边都同步回显 |

**顺带修掉的一个逻辑问题**：原来「耳机断开」无条件结束录音。现在区分记录来源——

| 记录是怎么开始的 | 耳机断开时 |
|---|---|
| 连耳机自动触发（没手动干预过） | 结束记录（原有行为） |
| 手动开始 + 手机麦克风 | **继续录**（耳机与手机麦无关），只提示一句 |
| 手动开始 + 耳机麦克风 | 自动切到手机麦克风继续录（不因为耳机没电/摘下就断掉整场会议） |
| 录音中手动切过音源 | 视为手动接管，之后耳机再断开也不再结束记录 |
| 通话中（来电/微信语音） | 只提示，不停记录（服务自己等通话结束续录，v1.15 逻辑保留） |

- `RecorderService.EXTRA_SOURCE`（`phone` / `bt`）显式指定音源，不传则跟随偏好
- `RecorderService.ACTION_SWITCH_SOURCE` 切音源，内部复用 30 分钟定时切段的 `rotateSegment()`，一段都不丢
- `RecorderService.currentIsBtMic` 暴露**真实生效**音源（SCO 建立失败回退手机麦时，界面不会谎报耳机麦）
- `RecorderService.startedByBluetooth` 区分自动触发与手动开始，耳机断开逻辑据此分流

## 三·二十、接入其它录音设备 + WorkBuddy（v1.17）

**需求**：既能接钉钉、飞书这类会议/录音产品的产出，也能把草记接进 WorkBuddy。

**先说限制**：Android 沙箱下，草记既读不到钉钉闪记、飞书妙记的私有目录，也没有它们「把音频交给别的 App」的开放接口。所以适配只能走**系统标准协议**——这也是唯一合规且长期稳定的方式。

### 一、进得来（外部录音 / 转写稿）

| 入口 | 说明 |
|---|---|
| 分享到草记 | 钉钉闪记 / 飞书妙记 / 微信「文件」/ 录音笔 App → 分享 → 草记（`ACTION_SEND`，新增 `audio/*`、`text/*`、`application/*`、`SEND_MULTIPLE`） |

| 导入录音或转写稿 | 设置页新按钮，系统文件选择器多选（SAF，无需存储权限） |

支持的格式：

- **音频**：`m4a / mp3 / wav / aac / amr / ogg / opus / flac / 3gp / mp4 / wma / mka / webm`
  → 拷进应用私有目录（三方 URI 会在转写中途失效）→ 走自己的 ASR 流水线
- **文稿**：`txt / md / srt / vtt / json / docx`
  → 直接入库为「已转写」，**跳过 ASR**，只花一次大模型摘要的钱

`docx` 用 `ZipInputStream` 解 `word/document.xml` 抽段落，不引第三方库。

`TranscriptParser` 的关键处理不是"去时间轴"这么简单：

| 问题 | 处理 |
|---|---|
| 一句话被切成 3 条 cue | 按说话人**连读合并**，同一人连续 cue 合成一段，读起来才像对话 |
| 说话人与台词分行（钉钉闪记的写法） | 合并成 `说话人：台词` |
| 行内时间戳混杂（`00:12:34`、`[00:12]`） | 剔除时间戳保留台词 |
| 各家 JSON 结构不同 | 依次试 `transcript` / `text` / `segments[]` / `sentences[]` / `utterances[]` |
| 超长文稿 | 20 万字截断并注明 |

### 一、飞书 / 钉钉：为什么是「群机器人 Webhook」

| 方案 | 门槛 | 结论 |
|---|---|---|
| 企业自建应用 + OAuth | 要企业管理员建应用、配权限、走审核，个人用户根本走不通 | ❌ |
| **群自定义机器人** | 群里点几下就能拿到 Webhook 地址，两家都长期支持 | ✅ 采用 |
| 只做 ACTION_SEND 分享 | 要用户自己选聊天，不能「自动同步到项目群」 | 作为补充保留 |

两家协议只差三处，其余完全一致（HTTPS POST + JSON）：

| 项目 | 飞书 | 钉钉 |
|---|---|---|
| 加签密钥 | `"时间戳\n密钥"` 作为 **key**，对空串做 HMAC-SHA256 | 密钥作为 **key**，`"时间戳\n密钥"` 作为 **data** |
| 签名位置 | JSON body 里的 `sign` + `timestamp` | URL query（`&timestamp=&sign=`），签名需 URL 编码 |
| 成功判定 | `code == 0`（旧版是 `StatusCode`） | `errcode == 0` |

- **只看 HTTP 200 会误判成功**：两家都是「HTTP 200 + 业务错误码」表示失败。这里逐字段解析，并把常见错误码翻成「下一步该改什么」：

  - 钉钉 `300001` → access_token 无效（地址复制不全）
- **消息体只发摘要 + 待办**，不发原始逐字稿：群里没人读几千字，也避免过度外泄。原文只给「N 字，见 App」

## 三·二十二、中国方言与多语言识别（v1.19）

**需求**：适配中国方言和多语言识别。

### 一、先划清能力边界：哪些方言真的能认

这条赛道的真相是：**能不能识别方言，取决于服务端有没有那个方言的声学模型**，App 端传什么参数都改变不了这一点。Whisper 兼容协议的 `language` 只接受有限的 ISO-639-1 代码，`wuu`（吴语）、`nan`（闽南语）、`hak`（客家话）根本没有对应代码，传过去只会 400。真正做多方言的是讯飞、阿里、腾讯的专用方言接口，各自私有协议，不在 Whisper 协议里。

所以 App 的做法是**把话说清楚**，而不是假装全都支持：

| 语言 / 方言 | 硅基流动 SenseVoice | OpenAI Whisper | 实际行为 |
|---|---|---|---|
| 普通话 | ✅ `zh` | ✅ `zh` | 直接传 |
| 粤语（广东话） | ✅ `yue`（训练集含粤语） | ⚠ 只能传 `zh`，仍会输出粤语用字（多为繁体） | SenseVoice 传 `yue` 真正生效；Whisper 降级为 `zh` + 本地繁转简 |
| 四川话 / 东北话 | ⚠ 按 `zh` | ⚠ 按 `zh` | 两者都属官话，与普通话字面接近，字面准确率可接受 |
| 吴语 / 闽南语 / 客家话 / 湘语 / 晋语 | ❌ 无原生支持 | ❌ 无原生支持 | 按 `zh` 送，**设置页与详情页都会明确告知「本次按普通话识别」** |
| 英 / 日 / 韩 | ✅ | ✅ | 传 `en`/`ja`/`ko`，摘要仍用简体中文输出 |
| 中英混说 | ⚠ 会把英文按发音硬转汉字 | ✅ 推荐 | 走自动检测 |

### 二、三层处理：选语言 → 换算能力 → 归一化

```
设置里选「想识别什么」（15 项，含 7 种中国方言）
   ↓
SpeechLangs.plan(lang, provider)  ← 按所选服务的能力换算
   ↓  支持 → 直接传；不支持 → 降级 zh + 记下调级原因
AsrClient：四级降级链（完整参数 → 去说话人 → 去 language → 去热词）
   ↓  只在服务端明确 400/422 时降级，网络错误不重复打
文字后处理：去零宽字符 → 繁转简（可选保留）
   ↓
LlmClient.normalizeDialect：方言口语 → 普通话书面语（可关）
   ↓
摘要提示词按语言改写（外语 → 中文摘要；方言 → 先理解再书面化）
```

关键点：

- **`language` 不再硬编码 `zh`**。原实现里这一行是 `addFormDataPart("language", "zh")`，等于永远按普通话识别——用户说粤语，服务端也只会往普通话上靠。现在由 `SpeechLangs.plan()` 按服务能力换算。
- **降级要留痕**。`Transcript` 带 `langId` / `downgraded` / `note`，写进会话表的 `lang` 字段，详情页显示「识别语言：吴语（上海话）· 本次按普通话识别」。
- **`auto` 的处理按服务区分**：SenseVoice 接受字面量 `auto`，Whisper 不接受（会 400），后者改为**不发这个字段**，等价于自动判断。

### 三、繁转简：为什么不能随手 replace

粤语与港台口音的结果默认就吐繁体（`今日嘅會議`）。不转，中文用户读着割裂，搜索也会漏（同一词两种字形）。

表取自 OpenCC 的 `TSCharacters`（Apache-2.0），只收**单字一对一**的可靠映射，共 3221 组，打包在 `assets/t2s.txt`（19.7 KB，首用加载一次常驻）。

**故意不转的字**（一对多的经典翻车点）：

| 字 | 若强行转 | 后果 |
|---|---|---|
| 著 | 着 | 「著名」→「着名」 |
| 台 | 台 | 「台湾」→「台湾」误伤 |
| 面 / 里 / 云 / 松 | — | 古字与简体共用，转了反而错 |

`乾` 也在排除名单里：`乾燥` 该转、`乾隆` 不该转，宁可留着不改。粤语用字（`唔 / 嘅 / 咗 / 佢 / 哋`）本身没有简化形，转换后仍在，语义不受影响。

### 四、方言口语 → 普通话书面语（多花一次大模型调用）

为什么值得多花这一次：

1. **转写稿是给人看的**。「唔該晒，聽日下晝三點喺會議室傾」自己看懂没问题，转给同事、写进周报就没法用；
2. **摘要质量**。方言词容易被大模型当成语气词丢掉（「唔该晒」里的信息量就没了），先归一化再总结，待办与承诺的漏检率明显下降。

出口做**长度畸变校验**：结果短于原文 35%（模型偷懒写总结）或长于 220%（模型大段发挥）一律丢弃，退回原文——宁可用方言原话，也不要一份被篡改的稿子。

原始转写**完整保留**在 `transcript`，归一化结果存在新列 `transcriptStd`。详情页顶部可一键切换「查看原话 / 查看普通话版」，导出 Markdown 时优先用普通话版。

### 五、本地方言检测：事后纠错比事前设置更有用

用户装了 App 就直接录音，不会先去设置页选方言。结果是：说粤语、按普通话认，满屏错字，用户以为是 App 不准。

`SpeechLangs.detect()` 用方言特征词做一次轻量检测（每方言 8-15 个高频词，如粤语 `唔 / 嘅 / 咗 / 佢 / 冇 / 睇`）：

- 阈值：命中 ≥3 次**且**每千字 ≥10 次，避免个别词偶然出现就误判；
- 纯外文场景改用字符占比判定（假名 >15% → 日语，谚文 >15% → 韩语，拉丁 >70% → 英语）；中英混说按英文词占比 15%-60% 判定；
- 命中且与当前识别语言不符时，详情页直接给入口：「疑似粤语（唔、嘅、咗 共 17 处），点这里可按粤语重转」——点了就走 `enqueue(sessionId, langOverride)` 重转，**不动全局设置**，旧待办一并替换避免堆积。

### 六、热词表：方言与专名最划算的一招

设置页新增热词输入框（逗号分隔，上限 60 词），如 `虞懋府, 璟珹服务, 出租率, 免租期`。

- 只有声明了 `supportsPrompt` 的服务会发（Whisper 系支持；硅基流动 SenseVoice 没有这个参数，发了会 400）；
- 用户填了热词但服务不支持时，保存会明确提示「热词表暂不生效」，不做无声忽略；
- 方言录音里，人名和公司名是最容易错的部分——模型有词表兜底，比任何后处理都有效。

## 三·二十三、项目归属：从「靠名字猜」到「有档案、有证据、可纠正」（v1.20）

用户反馈：**不同项目、不同事项的分类不清晰，常常把这个项目的事记到另一个项目，AI 分析也不够准。**

### 一、先定位根因（四条，都是结构性的，改提示词治不好）

| # | 根因 | 后果 |
|---|---|---|
| 1 | 「已有项目」清单来自 `SELECT DISTINCT project FROM sessions` | 清单是**模型历次输出的回声**。模型曾写下「城市之光项目」，库里就多一个和「城市之光」并存的假项目，各挂一半记录 |
| 2 | 清单只有名字，没有任何判别特征 | 模型不知道「盛懋中心」是写字楼、「城市之光」是公寓，更不知道各自涉及哪些客户与楼栋。名字越像越容易串 |
| 3 | 提示词写「尽量复用已有项目名」，还把清单放在正文第一行 | 模型倾向**填一个**，哪怕原文根本没提项目——这是「记到另一个项目」的直接来源 |
| 4 | 输出没有校验，详情页也不能改 | 模型写「城市之光项目」就落库成新项目；用户发现错了也没有纠正入口 |

### 二、五项改造

**1. 项目升级为「档案」**（新表 `projects`）

每条档案 = 规范名 + 别名 + 线索词 + 一句话说明。落库只写规范名，比较时放宽：
`城市之光 / 城市之光项目 / 城市之光 ` 归一化后视为同一个项目（去空白、全半角、繁简、`项目/工程/小区` 等尾缀）。

**2. 存量碎片自动归并**（首次启动时一次性执行）

按归一化分组，**记录最多的写法**当规范名，其余并入并把旧写法记成别名，会话与待办在同一个事务里迁移。之后模型写哪种叫法都能落到同一条——统计不再各算一半。

**3. 分析前做候选预筛，连特征一起给**

不再把整个项目清单丢过去，而是按原文命中别名/线索词打分，只给最相关的 ≤8 个，每条附上别名、线索词、说明和「平时聊什么」（该项目最近 3 条标题）。清单短了、信息多了，模型才可能选对。

**4. 强制「抄证据」，抄不出来必须留空**

这是本轮最关键的一条。提示词要求：

```
4. projectEvidence 必须从原文里照抄一句话，不能概括、不能补写、不能拼接。
   抄不出这样一句话，说明第 2 条不成立，project 必须给空字符串。
```

代码侧再做一次校验：把模型给的 `projectEvidence` 拿回原文比对（按标点切片，任一片 ≥6 字命中才算有据），**找不到就判定整次归属不可信、直接留空**。模型最常见的失败不是「不知道」，而是「知道该填但没证据，于是编一句」——这一步专门拦它。

**5. 三道强校验 + 可纠正 + 会学习**

- 名字必须落档：精确 → 归一化 → 别名 → 唯一包含；落不上就留空，**从此不再产生「XXX项目」这类新碎片**；
- 置信度 <0.6 的记录，列表项目标签带 `?`，详情页显示「待确认」；
- 详情页项目条可点击修改（相关项目排前、全量兜底、可现场新建），并显示 AI 的判断依据；
- 纠正时把「项目名在原文中出现的上下文」记成线索词，下次同类说法自动命中；
- 项目详情页新增「识别线索」编辑（名称 / 别名 / 线索词 / 说明），改名走事务迁移，旧名自动留作别名。

### 三、一次会议涉及多个项目怎么办

- `otherProjects`：本次还明确提到的其它项目（同样只能来自候选清单），写进 `projectWhy`；

## 三·二十五、内页品牌标：从「玻璃托底」到「一体化立体徽章」（v1.22）

用户反馈：*「内页 logo 目前一条白线和内框，整个 logo 不立体优美，在红色底板上不精美。」*

### 一、诊断：v1.10 的玻璃托底自己成了问题

v1.10 的做法是「白色磨砂圆 + 1dp 白描边」托住红方块。它解决了「红压红看不见轮廓」，
但代价是引入了两样新东西，而且都在打品牌标的脸：

| 看到的 | 实际上是 | 为什么难看 |
|---|---|---|
| 一条白线 | 圆形的 1dp 白描边（`#A6FFFFFF`） | 它是**一圈**闭合的线，和方块没有关系，读起来像「套了个圈」 |
| 一个内框 | 圆里 `padding 7dp` 内缩的红方块 | **方压圆**，两者边长不匹配，留白时宽时窄 |
| 标本身平平的 | 红方块是**纯色填充** | 没有受光、没有暗部、没有投影——纸片一样 |

更根本的矛盾：这枚标在红顶栏上，红对红，靠外圈白线才勉强「被看见」；
外圈一旦拿掉，标就消失；外圈留着，就永远是一圈白线。**解法不是换外圈，是让标自己可以被看见。**

### 二、改法：去掉所有外圈，让徽章自己有体积

`drawable/ic_logo_mark.xml` 重画成一块**珐琅徽章**，外面不再有任何托底（`bg_logo_glass.xml` 已删除）：

| 层 | 做法 | 作用 |
|---|---|---|
| 落影 | 4 层同心缩放 + 下移（scale 1.092 / 1.064 / 1.040 / 1.018，translateY 3.4→1.5） | 矢量图**没有 blur**，只能靠多层低透明度叠出边缘过渡。颜色用偏红黑 `#4A0003` 而不是纯黑——纯黑落在红底上会发灰发脏 |
| 底板 | 竖向三段渐变 `#F0372A` → `#E00111`(40%) → `#98000A` | 上表面受光、下缘收暗，形成凸面。中段比顶栏红压深一档，是为了让**左右轮廓在中段也能咬住**（同色会糊掉） |
| 顶光 | 顶部 36% 叠白色渐隐（`#36FFFFFF` → 0） | 光打在圆弧顶端，这是「玻璃/珐琅」最直接的暗示 |
| 底压 | 55% 之后叠暗色渐隐至 `#4E3A0004` | 下缘「沉」进去，避免整块像浮贴 |
| 边光 | 上缘 1.6 单位描边，白 50% → 30% → 48% 处收掉 | **只在上缘、且渐隐收尾**，不是一圈白线；营造边缘反光 |
| 字母 | 白 C + 下沉 2.4 单位的同色系阴影（`#424A0003`） | 字从底板上浮起来；阴影不透出底板的洞 |

几何：视口 120×120，板面 100×100（留 10 单位给落影，避免被视口裁掉），圆角 25。
C 的外径/内径 = 28.2 / 15.87（板宽的 0.282 / 0.159），开口朝右 ±50°，**与桌面图标同一字形**，品牌不跑偏。

布局侧同步瘦身（5 个顶栏）：

| 位置 | 改前 | 改后 |
|---|---|---|
| 主页顶栏 | 40dp 圆 + `padding 8dp`（标 24dp） | **38dp 徽章，无 padding** |
| 记录详情 / 项目详情 / 语音速记 / 声纹录入 | 34dp 圆 + `padding 7dp`（标 20dp） | **30dp 徽章，无 padding** |

> 徽章自带留白，再套 `padding` 会把它缩小、落影也会被裁，所以 padding 必须一起去掉。

### 三、怎么验证的（没有设备也能看）

矢量图不能靠「看着差不多」交付，所以新写了 `docs/render-vector.py`：
直接解析 `ic_logo_mark.xml` 的 `pathData`、`group` 变换（scale/translate/pivot）、
`aapt:attr` 渐变与 `android:offset` 色标，按同一套坐标渲染成 PNG。

它当场查出了一个只有看图发现不了的问题：**C 的开口方向**。
把成图按环带半径采样 72 个角度，白色落在 50°→305°，缺口从 305° 到 50°（中心 ≈ 0°，即正右）——
与设计一致，没有偏转（这一步是数值判断，不是肉眼判断；肉眼在缩略图上容易被顶光干扰看成「开口朝右上」）。

对比图：`docs/logo-before-after.png`（由 `docs/logo-compare.py` 生成，
「改后」用的是**真实矢量图渲染**，不是另画一遍的示意稿）。

### 五、独立素材导出（`docs/export-logo.py`）

App 内的徽章是 VectorDrawable，导不出一张能直接贴到 PPT / 封面 / 应用市场素材里的图。
所以加了导出脚本，一份源码两种格式：

```bash
python docs/export-logo.py     # → 桌面 草记-logo-1024.png / 草记-logo.svg
```

| 处理 | 做法 |
|---|---|
| 位图 | 复用 `render-vector.py` 的渲染器按真实 pathData 绘制，超采样 3× 后 LANCZOS 缩回 1024 |
| 矢量 | 把同一份 XML 的 `group` / `path` / `gradient` 翻译成 SVG（`aapt:attr` → `<linearGradient>`），不另画一遍 |
| 投影 | App 内因为 VectorDrawable 无 blur，用 4 层同心缩放硬叠；独立成图时那 4 层在透明底上会露出 4 道灰弧，故改用**真高斯模糊** |

两个坑，都是看图看不出来、必须数值验的：

1. **投影形状不能用落影那 4 层**。它们是为了「无 blur 时也能看出边缘」而放大到 1.092 倍的，
   拿来当位图遮罩会又大又重（第一版出来像块浮在半空的牌子）。改用板面轮廓下移 4 单位再模糊。
2. **SVG 的 filter 不能挂在板面自己身上**。`feDropShadow` 挂在板面 path 上会把整块板面栅格化，
   渐变被截断出色带——实测绿色通道在 y≈378 从 13 掉到 0、到 y≈406 又跳回 13，成图上看就是一道横向分界线。
   改成用板面轮廓单独垫一层 `<path filter="url(#soft)">`，板面本身保持矢量精度，色带消失。

校验：PNG 与浏览器实际渲染的 SVG 逐像素比对，板面区域平均色差 **2.3 / 765（≈0.3%）**，
说明两份确实是同一份设计而不是各画各的；四角 alpha < 8（视口外无脏像素）、中心 RGB 为底板红。

## 十、已知限制与后续可做

**当前限制**
- 转写/摘要依赖网络与第三方 API（未配置时录音仍会保存，状态显示「待转写」，可稍后重试）
- **方言识别受限于服务端能力**：粤语可由 SenseVoice 原生识别；吴语 / 闽南语 / 客家话 / 湘语 / 晋语
  在 Whisper 兼容协议里没有对应语言代码，只能按普通话识别（App 会明确告知）。
  需要更强的方言能力，请用讯飞 / 通义听悟等专用接口转写后，把文稿导入草记
- 说话人区分需要**服务端返回带时间戳的说话人分段**。硅基流动 SenseVoice 与 OpenAI whisper-1 都只返回纯文本，
  选它们时「我 / 对方」不生效（App 会关闭开关并说明原因）；需要该能力请用 WhisperX / faster-whisper 一类的自建服务
- 通话录音导入依赖系统录音文件，且是**事后**导入（通话结束才有文件，非实时）
- 微信语音无法覆盖（系统限制）

**可以继续加**
- 本地说话人分离（切轮次 + 分段转写），让纯文本转写服务也能区分「我 / 对方」
- 端侧 whisper（离线转写，隐私更好，但包体大）
- 待办到期提醒的重复规则（如每周/每月）
- 多设备/多端同步（接 Supabase 或其他后端）
- 按月/按项目的复盘报告导出（PDF/CSV）
